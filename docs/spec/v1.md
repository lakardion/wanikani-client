# Exercise app v1: build spec

This spec is everything needed to build v1. Every decision in it is final. The terms in bold are defined in [`CONTEXT.md`](../../CONTEXT.md).

v1 is a single-user web app. It reads what the user knows from WaniKani and asks an LLM for one Japanese sentence per **Exercise**. The user translates the sentence to English, and an LLM grades the meaning. The **Explanation** shows after every **Exercise**.

Sources: the decision tickets under the map issue [Map: Exercise App v1](https://github.com/lakardion/wanikani-client/issues/1), the research in [`docs/research/`](../research/), and the prompt prototype in [`prototypes/exercise-prompts/`](../../prototypes/exercise-prompts/).

## Routes

- `/` is the exercise app.
- `/explorer` is the current SDK playground (`src/App.tsx` and its components), moved unchanged except for the fixes that the SDK 1.0.0 bump needs.
- There are no other routes and no API routes.

## Client and server boundary

The browser makes every WaniKani call. The WaniKani key never reaches the server. The server is stateless and has exactly two server functions, in one `"use server"` module:

- `generateExercise({ grammarId, sample, kanji })` returns one **Exercise**.
- `gradeAnswer({ grammarId, japanese, english, answer })` returns `{ score, feedback, pass }`.

The client sends the exercise back for grading because the server stores nothing. The server trusts it and applies only the Zod caps below.

## WaniKani key

- Storage: localStorage key `wanikani.apiKey`, shared with `/explorer`.
- No key saved: `/` shows the key form in place of the exercise.
- A settings popover changes or clears the key. Changing or clearing it also deletes `wanikani.knownItems`.
- The form note reads: "Use a read-only token. It is stored only in this browser. If it is exposed, regenerate it in WaniKani settings."
- A 401 from WaniKani goes back to the key form.

## Known items

Decided in #6. **Known items** are assignments at SRS stage 5 or higher, of type kanji, vocabulary or kana vocabulary, with hidden subjects excluded.

**Storage:** one localStorage key, `wanikani.knownItems`:

```ts
{ watermark: string; items: { [subjectId: string]: { type: "kanji" | "vocabulary" | "kana_vocabulary"; characters: string; meaning: string; partsOfSpeech: string[] } } }
```

`meaning` is the primary meaning. The size is about 300 KB.

**Sync** runs on every app load and from a **Refresh** button:

1. First run (no stored items): `assignments.paginate({ srs_stages: [5, 6, 7, 8, 9], subject_types: ["kanji", "vocabulary", "kana_vocabulary"], hidden: false })`, then `subjects.list({ ids })` in chunks of 200, and drop hidden subjects. Show a loading state with a progress count of subjects fetched. Do not use `client.app.learnedSubjects`: it has no progress hook.
2. Later runs: `assignments.paginate({ updated_after: watermark })` with no stage filter. For each assignment at stage 5 or higher, upsert it and fetch any missing subject by id. For each assignment below stage 5, remove it.
3. Watermark: client time captured before the sync starts, minus 10 minutes. Do not use the SDK's `syncSince` `fetchedAt`, which is taken after the fetch.
4. **Rebuild** in the settings popover deletes the store and runs the first-run path. Subject edits sync only this way.
5. A failed sync keeps the stored items and shows a dismissible error.

WaniKani does not expose `ETag` or `Last-Modified` over CORS, so conditional requests are not possible in the browser.

**Word sample**, built on the client for each **Exercise**:

- 150 **Known words**, each `{ characters, meaning }`, plus every **Known kanji** joined into one string.
- 5 **Word groups** of 30 words each: noun, verb, adjective, adverb, other. A word goes into the first group in that order that matches one of its `partsOfSpeech`. Godan, ichidan and suru verbs are verbs. い, な and の adjectives are adjectives.
- A group with fewer than 30 words is filled at random from the other words.
- Check the real WaniKani part-of-speech strings with a live key before writing the group mapping. `prototypes/exercise-prompts/known.ts` has a working mapping and a `posReport` helper.

**Empty state:** with fewer than 30 **Known words**, show "Not enough Guru+ vocabulary yet, keep reviewing." and disable generation.

## Grammar points

The 45 N5-N4 **Grammar points** in `prototypes/exercise-prompts/grammar.ts` move to a shared module that both client and server import. The client picks one at random for each **Exercise** and sends its `grammarId`. The server looks up the pattern and rejects an unknown id. No free text from the client goes into the generation prompt as grammar.

## Server functions

### Input caps (Zod)

Oversized input is rejected before any LLM call.

| Field | Cap |
|---|---|
| `sample` | 300 words or fewer |
| `sample[].characters` | 20 chars |
| `sample[].meaning` | 80 chars |
| `kanji` | 3000 chars |
| `grammarId` | One of the known ids |
| `japanese` (grading) | 200 chars |
| `english` (grading) | 400 chars |
| `answer` | 400 chars |

### `generateExercise`

1. Check the daily cap.
2. Call the LLM with `GENERATE_SYSTEM` from `prototypes/exercise-prompts/prompts.ts`, with one change: remove the `reading` field and the per-word `reading` from the schema and the prompt. The LLM schema is `{ japanese, english, breakdown: { text, meaning }[], grammarExplanation, example: { japanese, english } }`.
3. Kanji check: every kanji in `japanese` and `example.japanese` must be in `kanji` (`kanjiViolations` in the prototype). On a failure, regenerate once. On a second failure, return the error `exercise_failed`.
4. Add furigana with the tokenizer (see [Readings](#readings)): one for `japanese`, one for each `breakdown[].text`, one for `example.japanese`.
5. Return:

```ts
{ grammarId, japanese, furigana, english, breakdown: { text, furigana, meaning }[], grammarExplanation, example: { japanese, furigana, english } }
// furigana: { text: string; ruby?: string }[], the text in order, with the hiragana for each kanji run
```

The prototype has no vocabulary check, and the app does not add one. The prompt asks the model to use only the few listed words that fit one natural situation.

### `gradeAnswer`

1. Check the daily cap.
2. Call the LLM with `GRADE_SYSTEM` from `prototypes/exercise-prompts/prompts.ts`, unchanged. The prompt gets the Japanese, the reference translation, the **Grammar point** pattern and meaning, and the answer.
3. Return `{ score, feedback, pass: score >= 70 }`. The schema enforces an integer from 0 to 100.

### LLM call settings

- Set `provider: { require_parameters: true, sort: "price" }` so that OpenRouter routes only to endpoints that enforce the JSON Schema, cheapest first.
- Set `reasoning: { effort: "none" }`. Luna reasons at `medium` by default.
- Set `maxOutputTokens: 1000`. A normal call writes about 250 tokens. In 1 of 20 eval runs, Luna wrote 65,536 tokens for 368 s. The cap turns that into a fast error, and the kanji-check retry path generates again.
- Turn on the `response-healing` plugin.
- Validate every response with Zod.
- Do not throttle. The prototype's 3.1 s throttle was for eval bursts.

### Daily cap

An in-memory counter keyed by UTC date, in the server-function module. Each LLM call counts, regenerations included. At 300 calls, both functions return `daily_limit` without an LLM call.

The counter resets on cold start, on deploy, and per instance, so it only stops runaway loops. The hard ceilings come from OpenRouter:

- Free models: the platform cap of 1,000 requests/day, after a one-time purchase of $10 of credits. Without that purchase, the cap is 50 requests/day.
- Paid models: a credit limit on the key with `limit_reset: daily`, which returns 402 when used up. Keep auto top-up off.

The functions map an OpenRouter 402 or 429 to `daily_limit`.

### Errors

| Error | Client shows |
|---|---|
| `daily_limit` | "Daily limit reached." Generation stays off until reload. |
| `exercise_failed` | "Could not make an exercise." and a Retry button. |
| Any other failure | "Something went wrong." and a Retry button. |

## Readings

Readings come from the tokenizer, never from the LLM. The eval found wrong LLM readings (作文 as ぶんさく, 休んで as やんで).

- Package: `lindera-wasm-ipadic-nodejs`. Add it to Nitro `traceDeps`, or the build leaves out the `.wasm` file. Usage and build checks are in [`japanese-tokenizer.md`](../research/japanese-tokenizer.md).
- Furigana of a text: take the IPADIC kana reading (`details[7]`) of each token and convert katakana to hiragana. Align the reading to the token: each kanji run gets its part, and the kana in the surface get none (行っ/いっ gives 行 with い, then っ). When the kana do not line up, the whole token gets the reading. Tokens with no kanji or no reading get no furigana.
- The UI shows furigana with HTML `<ruby>` and `<rt>`, above the kanji, in the muted text color.
- An override table on the server fixes known IPADIC errors before the join. Start with the counter words: 一人 ひとり, 二人 ふたり, 一日 ついたち, 二日 ふつか, 二十日 はつか, 一つ ひとつ, 今日 きょう, 明日 あした, 大人 おとな. Add entries when a wrong reading shows up.
- An override key matches the joined surface of consecutive whole tokens. The longest match wins. IPADIC splits 一人 into 一 and 人, so a key never matches part of a token.
- Known risk: homographs such as 行った (いった or おこなった) can still come out wrong.

## Exercise loop

The **Session** is endless and ends when the page closes. A running count shows passes and **Exercises** done, in memory only.

1. **Waiting:** the first **Exercise** of a **Session** takes about 3 s. Show a loading state with the elapsed time.
2. **Answering:** show the Japanese sentence with no readings, and an English text input.
3. **Submit:**
   - An empty answer or `?` (after trimming) is a **Give up**. Go to the **Explanation** with no grading.
   - Otherwise, call `gradeAnswer`. On a **Pass**, go to the **Explanation**.
   - On the first failed answer, show the score and feedback and allow one retry.
   - On the second failed answer, go to the **Explanation**.
4. **Explanation:** show the last score and feedback (if graded), the sentence with furigana, the reference translation, the breakdown (text with furigana, meaning), the grammar explanation, and the example with furigana and its translation. A **Next** button goes on.
5. **Prefetch:** when an **Exercise** shows in step 2, start generating the next one. Keep at most one in memory. **Next** uses it, or waits for it if it is not ready. A reload loses it.

### Setup screens

The prototype is on the [`prototype/setup-screens`](https://github.com/lakardion/wanikani-client/tree/prototype/setup-screens) branch, variant A.

- A slim header holds the app name and, when a key is saved, a gear button that opens the settings popover.
- Each setup state is one centered card: the key form (title, one-line intro, password field with the note under it, a full-width "Save and sync" button), the first-run sync, and the empty state.
- First-run sync: a spinner in the card title, a progress bar, and an "n / total items" count.
- Empty state: the empty-state text, a badge with the known-word count out of 30, and a disabled "Generate exercise" button.
- Sync error: a destructive alert under the header with a close button. The page under it stays usable.
- Settings popover, top to bottom: the known word and kanji counts and the last sync time; Refresh and Rebuild side by side, with a note that Rebuild downloads everything again; then Change key and Clear key. Change key shows the key form inside the popover. A note says that changing or clearing the key deletes the stored items. Refresh shows a spinner in its button while it runs.

### Exercise loop screens

The prototype is on the [`prototype/exercise-loop`](https://github.com/lakardion/wanikani-client/tree/prototype/exercise-loop) branch, variant B (`prototypes/ui/loop.html`).

- No cards. The setup header stays. Under it, an outline badge shows the running count: "✓ passes · Exercises done".
- Waiting: a spinner in the middle of the screen, the elapsed time as `m:ss`, and one line of text. The first **Exercise** reads "Generating the first exercise." A **Next** that waits for the prefetch reads "The next exercise is still generating."
- Answering: the Japanese sentence in large type in the middle of the screen, with no readings. A bar pinned to the bottom holds the English input, a **Give up** button, and a Check button. **Give up** submits an empty answer.
- Grading: the input and the buttons are disabled, and the Check button shows a spinner and "Grading".
- First failed answer: a muted bubble under the sentence shows the score and the feedback. The Check button reads "Try again".
- Explanation: the sentence moves to the top of the screen, with furigana above its kanji. A bottom sheet (drawer) opens over the lower part of the screen, at most about 60% of its height. A tap outside does not close it. Top to bottom, the sheet shows a badge ("Pass · score", "Not passed · score" or "Gave up") with the feedback under it, the reference translation, the breakdown (text with furigana, and the meaning), the **Grammar point** (pattern, meaning, explanation), and the example (Japanese with furigana, translation). The sheet content scrolls. **Next** is pinned to the bottom of the sheet.
- A failed `gradeAnswer` call keeps the sentence and the answer, and shows the error alert under the sentence. Check sends the same answer again. A failed call does not use the retry.
- Errors replace the sentence in the middle of the screen. `daily_limit` is a neutral alert with "Generation stays off until you reload the page." and a disabled **Next**. `exercise_failed` and other failures are destructive alerts with a Retry button.

## Tests

Vitest covers the pure logic only. There are no component tests and no E2E tests. The units:

- **Word sample** grouping: the group order, the part-of-speech mapping, and the fill of short groups.
- Kanji check (`kanjiViolations`).
- Furigana: the alignment of each token reading to its kanji runs, tokens without a reading, katakana to hiragana, and the override table.
- **Give up** and **Pass** rules: empty or `?` after trimming, and `score >= 70`.

Each build step checks its result on a phone on the Vercel deployment.

## Hardening

- CSP is a static header set after `next()` in SolidStart middleware, in production only: `default-src 'self'; script-src 'self'; style-src 'self'; connect-src 'self' https://api.wanikani.com; img-src 'self' data:; base-uri 'none'; frame-ancestors 'none'; form-action 'self'`. Do not use Nitro `routeRules` headers. In the current release, a `/**` header rule sends static assets to the function too.
- No third-party scripts.

## Build order

Each step deploys and works on its own. Step 3 is the first usable version.

1. **Skeleton.**
   - Add `@solidjs/start`, `@solidjs/router` and `nitro`, and set the plugins in `vite.config.ts`.
   - Replace `index.html` and `src/index.tsx` with `src/app.tsx`, `src/entry-client.tsx` and `src/entry-server.tsx`.
   - Move `App` to `src/routes/explorer.tsx`, and stub `src/routes/index.tsx`.
   - Bump `wanikani-sdk` to `^1.0.0` and fix the explorer registry.
   - Deploy to Vercel, check `/explorer`, turn on Vercel Authentication for all deployments, and add the CSP middleware.
2. **Key and known items:** solid-ui setup and the palette, key form, settings popover, sync (first run, incremental, Refresh, Rebuild), empty state, loading and errors.
3. **Generation:** Vitest setup, grammar module, **Word sample**, `generateExercise` with the kanji check and the daily cap. The UI shows the sentence and a Reveal button that shows the **Explanation** without readings.
4. **Grading:** `gradeAnswer`, the answer input, retry, **Give up** and the count.
5. **Readings:** tokenizer, override table, readings in the **Explanation**.
6. **Prefetch** of the next **Exercise**.

## Paid step

v1 uses the paid `openai/gpt-6-luna`. Before the first deploy with it:

1. Set a daily credit limit on the OpenRouter key (`limit_reset: daily`), with auto top-up off. $1 a day is more than 300 calls.
2. Keep the prefetch.

The eval in `prototypes/exercise-prompts/out/report.md` compared six paid models (20 generations each, 24 graded answers × 2):

| Model | Kanji-clean | Median gen | Gen cost | Grading in band |
|---|---|---|---|---|
| `openai/gpt-6-luna` | 19/20 | 2.8 s | $0.00038 | 47/48 |
| `google/gemini-3.5-flash-lite` | 16/20 | 2.0 s | $0.00143 | 46/48 |
| `deepseek/deepseek-v4-flash` | 11/20 | 8.2 s | $0.00019 | 39/48 |
| `anthropic/claude-haiku-5.5` | 8/20 | 3.1 s | $0.00055 | 34/48 |
| `google/gemini-3.1-flash-lite` | 7/20 | 2.3 s | $0.00115 | 43/48 |
| `mistralai/mistral-small-2603` | 1/5 | 7.5 s | $0.00050 | 18/20 |

Luna also wrote the most natural sentences. Gemini 3.5 wrote broken Japanese in about 1 of 4 runs (for example 私会行たい). Mistral was rate-limited upstream in 15 of 20 runs. The Luna cost leaves out the one runaway call ($0.033).

## Known risks

- **Latency:** about 3 s per generation (median of 20 eval runs). Without `maxOutputTokens`, a runaway call can pass the Vercel Hobby limit of 300 s.
- **Naturalness:** about 3 in 20 Luna sentences are stilted, such as 兄は古いが、まだ使える (eval in `prototypes/exercise-prompts/out/report.md`).
- **Model goes away:** if OpenRouter drops the model, change `OPENROUTER_MODEL`. The next choice is `google/gemini-3.5-flash-lite` without the `reasoning` setting (it rejects `"none"`).
- **Readings:** homographs, see [Readings](#readings).

## Non-goals

Out of scope for this effort:

- Access for more than one user.
- WaniKani key storage on the server.

In scope for later versions, not v1:

- Exercise history and progress persistence (a database).
- Other exercise types: fill-in-the-blank, Japanese production, multiple choice, listening.
- Review scheduling of missed **Exercises**.
- Tuning the pass threshold of 70.
